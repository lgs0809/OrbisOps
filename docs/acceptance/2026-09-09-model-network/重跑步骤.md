# 自然语言输入与模型网络恢复

仅本机 OrbisOps 隔离验收环境。页面 http://127.0.0.1:3302，后端 http://127.0.0.1:18089；业务目标 http://127.0.0.1:18262/version。账号沿用正常初始化流程创建的 `ops_acceptance_admin`，密码存放在 `deploy/.acceptance-private/admin.json`，不放入报告。MySQL 端口 13362，数据库 `orbisops_acceptance`；只读核验 SQL 随每个 Run 的检查结果保存。

## 接入原有已授权模型

在仓库根目录执行。脚本只从现有 `deploy/orbisops.env` 读取模型网关地址和密钥，写入权限为 600 的隔离配置；不会注册新账号或启用新的付费资源。主对话使用小模型 `gpt-5.6-luna`，大模型保留 `gpt-5.6-terra`，不使用 gpt-5.5。向量与重排模型迁移单独处理，后台演化和记忆模型开关也不会被一起打开。

```sh
python3 scripts/enable-acceptance-models.py --output /tmp/orbisops-model-config.json
mvn -B -f server/pom.xml -Dtest=OpsRuntimeConversationContextCoordinatorTest,OpsRuntimePromptAssemblerTest,OpsModelNetworkRecoveryTest,OpsModelProviderFailureClassifierTest,OpsMcpCoreSchemaDisclosureTest,OpsRuntimeModelResolverTest,OpsRuntimeResourceAssemblerTest -Dsurefire.failIfNoSpecifiedTests=false package > /tmp/orbisops-model-package.log 2>&1
python3 scripts/deploy-tested-acceptance.py --test-log /tmp/orbisops-model-package.log --output /tmp/orbisops-model-deployment.json
python3 scripts/seed-acceptance-models.py --output /tmp/orbisops-model-seed.json
```

模型与 Provider 的种子通过正常管理 API 导入；同内容重复执行不重复建记录，已有冲突配置不会覆盖。数据库只存环境引用，不存模型密钥明文。前端变更后在 `web` 目录执行 `npm run verify`，将成功日志传给 `scripts/deploy-tested-web-acceptance.py`，该脚本核对容器内所有静态文件字节与本次构建一致。

## 用户实际操作

在页面选择「隔离验收项目 A」和「默认助手」，新建对话，输入：

> 帮我看一下隔离验收项目 A 里，验收服务 A1 当前部署的版本。请实际查询，只读检查，用中文告诉我结果和依据。

用户不填写 JSON、服务 ID 或时间戳。系统向模型提供当前时间；模型通过工具目录读取 Schema，通过项目 Skill 资源定位服务，再查询真实目标。Skill 中的 `fixture-1` 只是验收预期，必须取得新的真实版本回执后才能回答。

从页面「查看运行」取得实际 Run ID，再执行：

```sh
python3 scripts/inspect-natural-language-run.py --run-id "$ORBISOPS_BROWSER_RUN" --output /tmp/orbisops-natural-query.json
```

脚本只读数据库和实际组件，保留 `*-inspect.sql`、TSV、模型事件、完整工具回执、独立 MCP 查询账本及目标版本。普通 Chat 不一定有 Workflow dispatch 行，检查按持久化远端回执中的 queryId 关联 MCP 独立账本。要求自然语言输入、模型请求与响应身份一致、数据库回执 Hash、MCP 响应 Hash、目标实际版本和回答全部一致；单独的 Run SUCCEEDED 不算通过。

## 可控 503 + 真实模型浏览器测试

```sh
python3 scripts/start-model-recovery-acceptance.py --state-dir /tmp/orbisops-model-recovery-run
```

该目录必须是本次新建目录，避免覆盖旧证据。专用容器只监听后端共享网络空间的 127.0.0.1:8382，不开放主机或公网端口；最多处理 24 次物理请求，前两次注入 503，后续原样转发到已有 HTTPS 网关。它只记录请求/响应 Hash、状态和耗时，不保存提示词、密钥或模型正文，不生成任何成功模型响应。

页面新建对话，明确选择说明为「仅用于本地网络故障恢复验收；仍由真实 Luna 推理」的 Luna 绑定，再输入上面的中文问题。检查实际请求记录里的模型 ID 为 `ops-acceptance-luna-recovery`；观察两次重试提示及最终回答，用同一只读脚本核验实际资源。`transport.sqlite` 保存 503 与真实转发记录：同一次请求的前两次失败和第三次转发必须具有相同请求 Hash。

测试结束只停止专用容器；其绑定目录和数据库证据仍保留：

```sh
docker stop orbisops-acceptance-model-fault
docker rm orbisops-acceptance-model-fault
```

随后页面选择「默认模型」。专用测试模型仅用于这一受控故障场景；普通项目默认仍指向原网关。后端重新创建网络空间后，旧故障容器也需要停止，并用新的证据目录重建。不能为了复测清空旧账本或删除业务数据卷。

## 重试边界

一次原始模型 HTTP 请求最多 3 次物理尝试，带退避与抖动，遵守 Retry-After 和同一节点截止时间；SDK 内层重试保持 1 次。短暂 503、限流、连接/读超时、未收到任何模型片段的空流可以有限重试。鉴权/额度/非法请求、取消、截止时间、模型身份错误和已接收到部分响应的流不重放。重试边界位于模型 HTTP 请求外侧，不包裹 Agent 或工具循环，已成功工具不会重复执行。

16 个本机真实 HTTP/SSE 故障用例覆盖重试、8 个并发请求、取消、持续分块截止时间、工具执行一次、部分输出和错误身份；它们的模型内容是协议 fixture，不计真实推理效果。浏览器实测的真实模型结果单独保存。用户消息仅保存原话，模型内部的指代解析保留在审计元数据，不再拼接进用户正文。
