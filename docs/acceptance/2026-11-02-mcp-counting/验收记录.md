## 保留的失败与修正

- 首次聚焦测试因测试代码局部变量声明写法未编译；修正后原 19 项实际通过，首个编译失败日志保留。
- 第一次完整协调器因输出文件前缀与其保留旧证据检查冲突，未执行测试；使用新前缀重跑，没有删原记录。
- 初次 XML 复核启动过早，协调器尚在计算最终源码/类/JAR 身份，生成未完成状态的 FAIL；补充 RUNNING 拒绝检查后，在协调器完成后重新复核 PASS。不是断言失败，也没有把旧不完整结果覆写。
- 恢复原后台 Episode 时出现实际瞬态模型失败；现有独立持久化退避随后自动恢复，三个原 Episode 的响应模型身份均核对为 Luna。没有替换模型或改原失败状态。
- 补跑原环境条件跳过用例时，自定义启动器使用带日期后缀的 Workflow 库，但旧用例故障注入固定指向 `orbisops_workflow_regression`，导致一项“应注入失败”断言未触发（43 通过/1 失败）。随后按旧固定库执行，又因保留的历史合成过期 Run 占满有界候选查询，15 个用例找不到自身候选（29 通过/15 错误）。两轮原日志及启动器完整保留，没有删旧行造绿。最终将故障注入目标绑定实际 JDBC database 并严格限制回归库名，独立库补跑 44/44 通过；原 helper 默认创建新的隔离回归库、允许显式安全库名，再以原 schema 范围用户实跑 31/31。
