# OPS-04 扩展：不同症状的自动事件归组

这批实现可解释的自动关联：告警内容不必相同，不等待人工确认；证据不足时先独立调查，后来出现共同上游异常再自动归组。原始告警、调查运行和历史决定均保留，归组不等于根因确认，也不授予执行权限。

## 调研依据与项目选择

Alertmanager 的去重、通知分组和抑制适合降低告警风暴，但配置标签分组本身不负责证明跨组件因果关系。[Prometheus 官方文档](https://prometheus.io/docs/alerting/latest/alertmanager/)

仅有时间相近不足以判定根因；拓扑、交易上下文以及同时发生的组件异常能提供更强的关联证据。[Dynatrace 原理说明](https://docs.dynatrace.com/docs/dynatrace-intelligence/root-cause-analysis/concepts)

COLA 将时空关联和知识辅助分析结合，说明可以采用混合路径，而非为每种数据库或中间件故障手写一对规则。[COLA 论文](https://arxiv.org/abs/2403.06485)

本项目据此选择第一版“时间＋依赖＋共享标识”的确定性关联策略；没有复现上述产品、论文算法或它们的准确率。尚未接入模型语义判别，也不把缺少关系证据的相似文本强行合并。后续模型仍限 Luna/Terra，不能静默换模型。

## 当前规则

- 硬边界：同项目、同明确环境。没有 onset、明显未来时间、含义不明的通用标识，不参与猜测归组。
- 同一 correlation_id / trace_id：起始时间差最多 15 分钟。
- 其他传播关系：起始时间差最多 3 分钟。可以是共享资源、同实例、同次变更作用于关联实体、直接依赖，或共同邻接实体也在异常。
- 依赖边必须具有来源和有效期，并覆盖两次异常的发生时间。公共邻接实体超过 8 条边时不使用该捷径，避免将大量无关症状吞入一个组。
- 每组最多 32 个成员、最多查看 100 个候选组、最多 256 条拓扑边。新成员必须和原始锚点满足规则，避免任意传递式合并。
- 分数仅是规则优先级，不是置信概率。锚点是归组参照，不标为根因。
- 共同上游告警晚到后自动重新检查邻近组；原组保留 merged_into，合并原因单独记录。
- 恢复通知追加原故障，不直接将 Incident 标为恢复。没有已落地方案时，恢复验证仍按既有流程拒绝。

上述时间与容量是本项目首版取舍，不是论文结论或普遍最优参数。当前依赖拓扑经管理员 API 导入；验收脚本从真实本地容器部署关系生成，没有自动从全量调用链发现生产拓扑。

## 并发和持久化

完全重复告警继续使用原 fingerprint 聚合、debounce 和 outbox。跨症状归组读取已持久化的鉴权告警账本，每 5 秒有界补扫；MySQL 短事务内按项目和环境串行提交归组，网络和模型调用不进入锁区。event_id 唯一记录使重放不重复计数，事务中断可以重试；未处理记录不因超过一天而消失。

归组作为旁路投影，不阻塞成员启动调查。当前每个不同告警仍单独执行有次数上限的 B 图取证；尚未实现跨成员共用一次根因调查、合并已经执行中的工具请求。也未解决“外部 Run 已提交而 outbox 确认前进程崩溃”的通用未知投递结果问题。不能据此声称所有外部动作 exactly-once。

## 本地重跑

仓库根目录：OrbisOps 仓库根目录。底座已使用 `orbisops-acceptance` Compose 隔离部署，依赖及初始化沿用前批步骤。不要执行 down -v、清库或替换用户已有卷。

```sh
python3 scripts/local-acceptance.py status
python3 scripts/seed-alert-correlation.py
python3 scripts/test-alert-correlation-runtime.py --output /tmp/orbisops-correlation-runtime.json
python3 scripts/test-alert-correlation-restart.py --output /tmp/orbisops-correlation-restart.json
```

seed 可重复导入，保留其他规则和拓扑。发现同名验收规则或同边的来源不一致会停止并保留原数据；初始化本身不启用规则。

故障脚本会短暂停止本项目的 workflow-target，确认实际 Docker 状态和 Prometheus up=0 后发送三种不同症状的签名告警。先两个下游各自调查，第三个共同资源告警到达后自动合并。它不是注入 Redis→MySQL 死锁，也不能证明已验收任意跨组件故障传播。finally 恢复目标和规则原状态，不清除业务记录。运行前停止验收流量脚本，以便核对停机前后业务事实不变。

重启脚本只重启隔离 backend，并恢复两个 MCP 服务，保留卷；检查归组和审计记录不重复、无效拓扑输入 400 且不修改原拓扑、历史 MCP 回执与同 Run / 同项目数据库记录和哈希一致。该脚本要求先成功执行上面的真实故障用例。

MySQL 的只读检查文件是 `scripts/fixtures/ops04-correlation-inspect.sql`。它展示当前组、旧组合并去向、成员状态、决定历史、投递 Run 与工具结果引用，不包含密码或完整业务载荷。

## 源码入口

- `domain/incident/correlation/`：通用关联信号、有效期拓扑和纯规则。
- `application/incident/AlertCorrelationApplicationService`：幂等观察、迟到证据重归组。
- `JdbcAlertCorrelationStore` / `JdbcAlertCorrelationSignalReader`：MySQL 事务与源账本补扫。
- `OpsAlertCorrelationJob` / `OpsAlertCorrelationController`：自动调度与项目权限 API。
- migration `080` / `ops-alert-incident-correlation.sql`：六张新增表，不改原始审批或 Incident 状态。
- `AlertCorrelationPanel.tsx`、`incident-center.tsx`、`incident-time.ts`：可见入口、依据、真实 Run 链接和 UTC 时间。
- `OpsMcpReportEvidenceReader` / `OpsStructuredReportService`：用保存的真实回执补历史事件查询状态，不改历史数据，不将查询成功渲染为业务正常。
