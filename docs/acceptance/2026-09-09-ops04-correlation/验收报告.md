复查命令使用 `ORBISOPS_C_EVIDENCE_FILE` 环境变量指向本机已采集的 `c-real-component-evidence-second.json`。请先设置该文件路径；变量不生成或代替运行证据。各批次交付中的原始执行日志保持不变。

截至 2026-09-09，本批代码已部署到本机隔离环境。不同告警内容可以自动归组，不等待人工；证据不足先各自调查，共同上游证据到达后自动合并。代码不枚举 Redis、MySQL 等产品组合。归组仍是关联假设，不等于根因确认。

## 通过

- 实际停止隔离业务目标后，先收到两个不同症状的下游告警，各自启动 B；共同资源告警晚到后自动形成一个三成员组。Docker Running=false、Prometheus up=0、三次真实 B 的 UNREACHABLE 报告及 MCP 回执相符。
- 六个并发重复通知没有额外 FIRST 投递；通知次数保留。恢复目标后发送正常签名恢复通知，每成员共四次通知；Incident 保持 VERIFYING，没有改库制造恢复成功。
- 实际重启后，事件组、次数、决定与合并历史完全一致。真实 MySQL 并发测试覆盖 51 个不同信号及重复处理、32 成员上限、事务回滚、迟到证据；两天积压仍能补处理。
- 项目 B 成员读取 A 返回 403；查看者修改拓扑返回 403；非法时间返回 400 且原拓扑不变。种子重复导入一致。
- CUA 实际点击工作台 → 事件归组 → 依据 → 成员 → Investigation → 原始运行；核对真实 Run ID、MCP 查询及报告。无已落地方案时，页面恢复验证按既有流程拒绝。
- 修复 UTC 被当作本地时间而多计八小时、运行 ID 显示为 run-0/run-1、已查询的 MCP 回执被旧报告误判为未查询。回执核对项目、Run、完整输出与哈希；查询成功仍显示业务判断 UNKNOWN。
- 后端本次实际执行 4702 项，4678 通过，24 跳过，0 失败/错误；前端构建、类型检查、49 个文件 / 137 项测试通过。只读检查 SQL 完整执行，输出保留。

## 失败记录

初次 MySQL 合并测试因 INSERT SELECT 的 occurrence_count 列歧义失败，已修复并复测。首次初始化在 Python 3.9 解析 Docker 纳秒时间失败，已修复。前端一次测试使用不兼容的宿主 node_modules 导致 Rollup 启动失败，改在独立 Linux 构建镜像运行通过。页面首次访问发现路由未注册和上述呈现缺陷，现已修复。原始失败日志与修复前截图均保留，不计通过。

- 自动从全量调用链发现生产拓扑、真实 Redis→MySQL 死锁级联、多集群规模效果、长期误合并/漏合并率。当前实际故障测试是共享本地进程停机下的不同监控症状，不能外推为上述场景都已通过。
- 单独修改拓扑后立即重算全部旧组尚未接入；新信号到来会触发附近组重算。没有批量历史拆组界面。
