# 本地部署产物与存储清理

本次本地清理先移除了 23 个停用的 `embedding-model-before-orbisops-contract-*` 历史容器、两个闲置镜像标签，以及仅匹配 OrbisOps／SemEvoSQL 的约 17.08 GB Docker 构建缓存。EvoKB 另移除了 72 份过期部署 JAR，约 9.57 GB，保留当前部署和两份相关历史验收产物。

用户随后确认只保留当前环境，并明确三个运行中的 旧工具服务 服务也没有使用，因此再移除了 81 个历史开发／验收／旧商城容器、三个该服务容器，以及 36 个无人引用的旧项目应用镜像。容器总数由 135 降至 28：OrbisOps 主验收环境 13、最新展示环境 5、SemEvoSQL 当前环境 4、EvoKB 及共享 embedding 共 6。主机可用空间已回升至约 54 GB；Docker 缓存统计与主机实际回收量存在共享层及回收时序差异，不能直接相加作为精确效果。

当前 `embedding-model` 的容器 ID、`708374…` 镜像、启动时间、运行配置和 `embedding-model-cache` 权重卷均未改变。113 个命名／匿名数据卷全部保留，源码、原始 SQL、截图和成功／失败报告保留。旧商城 Elasticsearch 的索引直接存于容器可写层，删除容器前已另存为约 75 MB 的私有压缩备份，并完整读取校验。完整 Docker 恢复配置含凭据，只保存在 Git 忽略的私有目录。`/ready`、检索适配器和 EvoKB 健康检查通过；真实浏览器仍能打开合同原文，正式问答验收没有中断。

清理也暴露了旧脚本对 `embedding-model:local` 标签的固定构建依赖，该标签已被清除。隔离修复改用当前已安装运行时的镜像 ID，经临时本地标签供 BuildKit 解析；关闭拉取和构建步骤网络，重复构建必须保持已处理应用源码的字节不变，部分处理或来源不符则拒绝。实际 Docker 重建及九份运行源码／底层依赖层核验通过，候选容器从未启动，验证后移除候选标签和临时容器。

后续部署的备份上限默认设为一份，明确保护紧邻的回滚容器，排除运行中容器、名称不匹配对象和其他数据卷。七项隔离检查通过。这四个构建／保留策略文件已在冻结问答及原生核验全部结束后按原始文件哈希检查应用。另用真实 Docker 临时容器验证了保留指定回滚版本与移除旧副本，三个临时容器全部清掉；已有七项维度／推理准入回归也通过。当前模型服务未重启或替换，仍是已经验收的镜像。

清理记录保存在本机证据目录 `work/full-acceptance-20261104-0940/` 的 `storage-*` 和 `ops-offline-*` 文件中，包括实际删除清单、构建命令、回收结果及清理后检查。原始运行报告保留，但已删除的过期二进制路径不能再直接运行。

## 固定运行时基础与恢复

清理后还发现旧后端／前端部署脚本依赖已移除的 `2.0.0` 基础标签；首次后端构建因此失败，原服务没有改变，失败记录保留。三类部署现在统一使用 `scripts/runtime_foundation.py`：首次从本机已安装组件固定一个运行时基础镜像，只追加标签，不增加文件系统层；基础 ID、运行配置指纹和来源收据写入私有目录。后续应用升级复用这个固定基础，不将上一版应用不断叠成新基础，也不静默拉取远端镜像。收据缺失、镜像缺失或运行配置漂移时明确拒绝。

后端与前端已完成实际构建、正常部署及升级后的固定基础复用核验；两个基础均保持 16 层，当前应用均 20 层。模型部署脚本也接入共享逻辑，本轮没有重新部署模型，因此不能声称模型基础切换已经实际运行。后续清理必须保留这些当前构建依赖以及当前 SemEvoSQL 执行镜像。

主环境恢复后，已移除完成且退出码为 0 的 migration 一次性容器，最终仍为 28 个容器：19 个运行、9 个暂停（SemEvoSQL 4、展示环境 5），113 个数据卷。当前磁盘约 49 GiB 可用。共享模型、检索适配器、知识库和 OrbisOps 正常；实际问答和运维方法由真实浏览器／原生数据分别验证，健康探针不代替业务验收。
