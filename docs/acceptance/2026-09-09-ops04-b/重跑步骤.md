# OPS-04 本机真实观测工作流

本批完成 B 的确定性指标、日志、慢 SQL 条件分支和一次 EXPLAIN 补查；A v1 完成固定巡检检查。Agent＋Skill 的模型调查、A 自动转 B、C、事件触发与防重仍在后续批次，不能将本批作为 OPS-04 全部完成的证明。

## 启动与初始化

在仓库根目录执行。所有服务使用 `orbisops-acceptance` 独立 Compose 项目，公开端口只绑定本机；种子脚本保留已有主键、订单、凭据和已审核策略。不要运行 `down -v`，不要对其他项目执行 stop。

```bash
python3 scripts/local-acceptance.py init
python3 scripts/local-acceptance.py up
python3 scripts/seed-local-acceptance.py
python3 scripts/start-observability-acceptance.py
python3 scripts/seed-observability-mcp.py --approve-read-only
python3 scripts/seed-business-workflows.py alert inspection
```

首次管理员通过正常 setup 入口建立；私密文件位于 `deploy/.acceptance-private/` 和 `deploy/.env.acceptance`，不应加入版本库或截图。`--approve-read-only` 会通过正常审批 API 留下审核人、schema hash 和时间，限定真实只读查询；不会写审批状态表。已有禁用或不同定义不会被静默覆盖。明确修改了定义源码时才使用 `--new-version`，旧版本和旧运行保留。

服务地址：UI `http://127.0.0.1:3302`，API `http://127.0.0.1:18089`，Prometheus `http://127.0.0.1:19062`，Elasticsearch `http://127.0.0.1:19262`，订单目标 `http://127.0.0.1:18262/ready`。只读 MCP 端口 18862 要求私密 Bearer token。

项目 A 的服务 1、2、3、4 分别对应正常、每十次一次 503、低流量、每五次一次实际 `SELECT SLEEP(1.15)`。订单来自隔离种子库，HTTP 时间、状态、SQL 耗时和 trace 均来自真实执行。这是明确的合成业务负载，不是生产事故或真实历史样本。

## 产生真实请求并验证

```bash
mkdir -p work/acceptance
python3 scripts/exercise-workflow-target.py --duration-seconds 1800 --output work/acceptance/load.json
```

请求程序只产生负载，不注入健康结论。完成后，从 `load.json` 的 `startEpoch` 计算告警时间 `floor(startEpoch) + 900` 并转换为 UTC ISO-8601，作为下方 `ALERT_TIME`；完整窗口为该告警前后各 15 分钟。当前告警可以立即运行，但未来部分必须保持未完整。历史查询限定近六天，旧验收窗口过期后应重新产生请求，不能伪造时间。

```bash
python3 scripts/test-business-workflow-runtime.py --service ops-acc-a-service-1 --alert-time "$ALERT_TIME" --expected NO_OBSERVED_ANOMALY --output work/acceptance/b-healthy.json
python3 scripts/test-business-workflow-runtime.py --service ops-acc-a-service-2 --alert-time "$ALERT_TIME" --expected OBSERVED_ANOMALY --output work/acceptance/b-errors.json
python3 scripts/test-business-workflow-runtime.py --service ops-acc-a-service-3 --alert-time "$ALERT_TIME" --expected INCONCLUSIVE --output work/acceptance/b-low-traffic.json
python3 scripts/test-business-workflow-runtime.py --service ops-acc-a-service-4 --alert-time "$ALERT_TIME" --expected OBSERVED_ANOMALY --output work/acceptance/b-slow-sql.json
python3 scripts/test-observability-access-runtime.py --output work/acceptance/access.json
```

断言交叉核对工作流 END 节点、数据库检查点、真实 MCP RPC 台账、完整工具信封与 hash、ES 和 MySQL 的 trace/订单/状态/耗时，以及请求开始时间＋实测耗时推导的完成窗口。Prometheus 使用真实采样时刻的 range vector；计数值为不外推的窗口内下界。整体 p95 合并兼容直方图，不平均实例 p95。

确认负载程序已结束，再运行故障恢复测试。测试只暂停本项目的 ES 和订单目标，并在 finally 中恢复容器，保留数据卷。ES 停机期间产生五次真实订单读取，检查恢复后补写且无重复；目标停机用真实 `up=0` 验证低流量仍判不可达，重启后核对持久计数器。

```bash
python3 scripts/test-observability-fault-runtime.py --full-window-alert "$ALERT_TIME" --output work/acceptance/fault-recovery.json
```

A 首版使用发起时最近五分钟。在连续负载至少两分钟、真实采样数达到 100 后，可以把上述 runtime 命令改为 `--workflow inspection`，服务 1/2/3/4 的预期分别是 `HEALTHY` / `UNHEALTHY` / `INCONCLUSIVE` / `UNHEALTHY`。这只验证 A 的固定检查部分，不能算自动调查分支已完成。
